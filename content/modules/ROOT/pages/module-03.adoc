= Technology and Supply Chain

[[module-goals]]

== Module Goals

*Own your software supply chain.*

Ingest, build, sign, attest and secure your software supply chain. Take control by working hands-on with cryptographic signing, verification, and Software Bills of Materials (SBOMs). These practices enable you to maintain sovereignty over your software artifacts and dependencies throughout their entire lifecycle.

== Getting your golden image

Having your own golden image ensures you have full control and visibility over the software components included, significantly reducing security risks and supply chain vulnerabilities. By downloading and building golden images yourself, you guarantee provenance and compliance tailored to your organization's requirements. Ownership of these images allows for faster recovery, reproducibility, and assurance that no unapproved changes or dependencies are introduced into your environments.

We'll be building a python based application to demonstrate the signing and verification process. 

.Procedure
. First, let's download and push a public image to your Quay instance. Run the following commands in the terminal:
+
[source,sh,subs="attributes",role=execute]
----
source ~/.bashrc
podman pull registry.access.redhat.com/ubi8/python-312:1-1775513555
podman tag registry.access.redhat.com/ubi8/python-312:1-1775513555 $QUAY_URL/$QUAY_USER/python-ubi-312:3.12-golden
podman push --remove-signatures $QUAY_URL/$QUAY_USER/python-ubi-312:3.12-golden
----
+
UBI images from Red Hat carry signatures; pushing to another registry may change layer layout, so `--remove-signatures` avoids the error _Would invalidate signatures_. You are still pushing the same image content.

You now have a container image in the local Quay registry.

== Rebuilding the Patient Portal Frontend

.Procedure
. Go to the `patient-portal-frontend` build directory in the Terminal tab on the right:
+
[source,sh,subs="attributes",role=execute]
----
cd ~/demo-applications/image-builds/patient-portal-frontend
----

. Replace both `FROM` lines so the build uses your Quay golden image instead of Docker Hub. The upstream Dockerfile currently uses `python:3.14-slim`; this substitution matches any `python:` tag so it still works if that version moves:
+
[source,sh,subs="attributes",role=execute]
----
sed -i "s|^FROM docker.io/library/python:[^[:space:]]*|FROM $QUAY_URL/$QUAY_USER/python-ubi-312:3.12-golden|g" Dockerfile
grep '^FROM' Dockerfile
----
+
Both stages must show your Quay golden image. If either line still says `docker.io/library/python`, the next build pulls from Docker Hub and skips the golden image you just pushed.

. Build the frontend container image:
+
[source,sh,subs="attributes",role=execute]
----
podman build -t $QUAY_URL/$QUAY_USER/patient-portal-frontend:1.0 .
----

. Push the image to your Quay instance:
+
[source,sh,subs="attributes",role=execute]
----
podman push $QUAY_URL/$QUAY_USER/patient-portal-frontend:1.0
----

. Resolve the *digest* of the image you just pushed. A tag such as `:1.0` is a pointer that can be moved to a different image later. A digest (`@sha256:...`) is the immutable checksum of that exact image:
+
[source,sh,subs="attributes",role=execute]
----
IMAGE=$QUAY_URL/$QUAY_USER/patient-portal-frontend:1.0
DIGEST=$(podman inspect --format '{{index .RepoDigests 0}}' "$IMAGE")
echo "$DIGEST"
----
+
[.console-output]
[source,bash,subs="+macros,+attributes"]
----
[lab-user@bastion ~]$ echo "$DIGEST"
quay.apps.<your-cluster>.<domain>/quayadmin/patient-portal-frontend@sha256:...
----
+
[IMPORTANT]
====
*Sign the digest, not the tag.* If you sign `:1.0`, you attest to whichever image that tag happens to point at when Cosign resolves it. Someone can later retag a different (unsigned or malicious) image as `:1.0`, and consumers who pull by tag will no longer be looking at the bits you signed. Signing `@sha256:...` binds the signature to one immutable artifact. Cosign warns when you pass a tag, and a future release will refuse tags entirely.
====

. Sign that digest. After `cosign initialize`, newer Cosign loads Fulcio and Rekor from the TUF `signing_config`. This lab still sets those service URLs (and the Keycloak OIDC issuer) in the environment, which Cosign treats as a conflict unless you turn the signing config off. `--new-bundle-format=false` keeps the classic `.sig` tag that `cosign tree` shows next:
+
[source,sh,subs="attributes",role=execute]
----
cosign sign --use-signing-config=false --new-bundle-format=false "$DIGEST"
----

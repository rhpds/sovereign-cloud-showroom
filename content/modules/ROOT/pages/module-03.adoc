= Technology and Supply Chain

[[module-goals]]

== Module Goals

*Own your software supply chain.*

Ingest, build, sign, attest and secure your software supply chain. Start from a verified link:{docs-hardened-images-url}[Red Hat Hardened Image^], then take control with cryptographic signing, verification, and Software Bills of Materials (SBOMs). These practices enable you to maintain sovereignty over your software artifacts and dependencies throughout their entire lifecycle.

[[golden-image]]
== Getting your golden image from Red Hat Hardened Images

A golden image is only as trustworthy as its `FROM` line. Public tags such as `python:3.14-slim` on Docker Hub move, and they are not the runtime Red Hat builds, signs, and CVE-patches for production.

link:{docs-hardened-images-url}[Red Hat Hardened Images^] (Hummingbird) are a no-cost catalog of *minimal, signed* runtimes at `registry.access.redhat.com/hi/…`. They are not a general-purpose UBI image: the standard runtime has no package manager or shell, which shrinks the attack surface. The *-builder* variant includes `dnf` and `pip` so you can compile and install, then copy artifacts into the minimal runtime.

Browse the catalog at https://images.redhat.com/[images.redhat.com^]. This lab uses the Python 3.14 pair documented for custom application builds:

* *Builder:* `{rhhi-python-builder}`
* *Runtime:* `{rhhi-python-runtime}`

You will *verify* those published images with Red Hat's Hardened Images key *before* you copy them into Quay. Later in this module you sign *your* application with in-cluster Trusted Artifact Signer. Those are two different trust roots: do not mix them.

We'll rebuild a Python patient-portal frontend on that hardened base, then sign the result.

.Procedure
. Verify the published Hardened Images with the Red Hat catalog key. This check uses Red Hat's public key and does *not* use your in-cluster Fulcio or Rekor:
+
[source,sh,subs="attributes",role=execute]
----
source ~/.bashrc
cosign verify \
  --key {rhhi-cosign-key-url} \
  --insecure-ignore-tlog \
  {rhhi-python-runtime}
cosign verify \
  --key {rhhi-cosign-key-url} \
  --insecure-ignore-tlog \
  {rhhi-python-builder}
----
+
`--insecure-ignore-tlog` is the documented pattern when you verify with a *key file* instead of a Rekor transparency log. See link:{docs-hardened-images-verify-url}[Verify the integrity of Red Hat Hardened Images^]. Expect a successful verify for both pull specs. If the key URL is blocked, stop and tell an instructor.

. Pull both variants, tag them into your Quay catalog, and push. `--remove-signatures` is required when the destination registry would rewrite layers and invalidate the Red Hat signature you just verified. You still push the same image content; your *application* signature comes later with Cosign and RHTAS. Workshop Quay uses a lab TLS certificate, so `--tls-verify=false` is required on login and push:
+
[source,sh,subs="attributes",role=execute]
----
source ~/.bashrc
podman login https://$QUAY_URL -u $QUAY_USER -p {quay_admin_password} --tls-verify=false
podman pull {rhhi-python-builder}
podman pull {rhhi-python-runtime}
podman tag {rhhi-python-builder} $QUAY_URL/$QUAY_USER/python-hi-314:3.14-builder
podman tag {rhhi-python-runtime} $QUAY_URL/$QUAY_USER/python-hi-314:3.14
podman push --remove-signatures --tls-verify=false $QUAY_URL/$QUAY_USER/python-hi-314:3.14-builder
podman push --remove-signatures --tls-verify=false $QUAY_URL/$QUAY_USER/python-hi-314:3.14
podman pull --tls-verify=false $QUAY_URL/$QUAY_USER/python-hi-314:3.14-builder
podman pull --tls-verify=false $QUAY_URL/$QUAY_USER/python-hi-314:3.14
podman images | grep python-hi-314
----
+
The last command must list both `python-hi-314:3.14-builder` and `python-hi-314:3.14`. If `podman build` later reports `repository not found` for `python-hi-314`, this push did not land — re-run this block before you edit the Dockerfile.

You now own both golden images in the local Quay registry: a builder you can compile on, and a minimal runtime you can ship.

== Rebuilding the Patient Portal Frontend

The upstream Dockerfile is a two-stage build. The first stage runs `pip install`; that needs the *builder* image. The second stage only copies the app; that should be the *runtime* image. See link:{docs-hardened-images-build-url}[Build custom application images^].

.Procedure
. Go to the `patient-portal-frontend` build directory in the Terminal tab on the right:
+
[source,sh,subs="attributes",role=execute]
----
cd ~/demo-applications/image-builds/patient-portal-frontend
----

. Point the *build* stage at your Quay builder image and the *run* stage at your Quay runtime image. The upstream Dockerfile uses `docker.io/library/python:3.14-slim`; this substitution matches any `python:` tag so it still works if that version moves. Hardened Images expose `python3`, so also update the entrypoint:
+
[source,sh,subs="attributes",role=execute]
----
sed -i "s|^FROM .* AS build|FROM $QUAY_URL/$QUAY_USER/python-hi-314:3.14-builder AS build|" Dockerfile
sed -i "s|^FROM .* AS run|FROM $QUAY_URL/$QUAY_USER/python-hi-314:3.14 AS run|" Dockerfile
grep -q '^USER root' Dockerfile || sed -i '/AS build$/a USER root' Dockerfile
sed -i 's|ENTRYPOINT \["python"|ENTRYPOINT ["python3"|' Dockerfile
grep -E '^(FROM|USER|ENTRYPOINT)' Dockerfile
----
+
You should see `python-hi-314:3.14-builder AS build`, then `USER root`, then `python-hi-314:3.14 AS run`, and `python3`. `USER root` is only on the builder stage so `pip install` can write packages; the runtime image still defaults to non-root. If either `FROM` still says `docker.io/library/python`, the next build pulls from Docker Hub and skips the hardened images you just pushed.

. Build the frontend container image:
+
[source,sh,subs="attributes",role=execute]
----
podman build --tls-verify=false -t $QUAY_URL/$QUAY_USER/patient-portal-frontend:1.0 .
----

. Push the image to your Quay instance:
+
[source,sh,subs="attributes",role=execute]
----
podman push --tls-verify=false $QUAY_URL/$QUAY_USER/patient-portal-frontend:1.0
----

+

----

----

[.console-output]

----
+
[IMPORTANT]
====
*Sign the digest, not the tag.* If you sign `:1.0`, you attest to whichever image that tag happens to point at when Cosign resolves it. Someone can later retag a different (unsigned or malicious) image as `:1.0`, and consumers who pull by tag will no longer be looking at the bits you signed. Signing `@sha256:...` binds the signature to one immutable artifact. Cosign warns when you pass a tag, and a future release will refuse tags entirely.
====

[source,sh,subs="attributes",role=execute]
